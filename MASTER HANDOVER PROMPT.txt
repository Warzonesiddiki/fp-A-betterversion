## XVIII-G. Section 4 — System Architecture

### Canonical Architecture Decision

```
Architecture: Modular Monolith → Selective Microservices (evolutionary)

Rationale:
- Phase 1: Modular monolith (faster velocity, easier debugging, 
  correct domain model first)
- Phase 2: Extract calculation engine + integration hub as services
  when load justifies it (evidence-driven, not premature)
- Phase 3: Full service mesh if multi-region scale demands it

This avoids distributed systems complexity before financial correctness
is proven. Wrong numbers in a microservice are harder to debug.
```

### Recommended Stack (must be probed against actual environment — K2)

```yaml
backend:
  language: TypeScript (Node.js) OR Python — decide at capability audit
  framework: 
    ts: Fastify (performance) with tRPC (type-safe API)

  calculation_engine:
```

## XVIII-H. Section 5 — Data Architecture

### Core Data Model (normalized to 3NF minimum)

```sql
-- TENANT (multi-tenancy from day one)
tenants (id, name, plan, fiscal_year_start, base_currency, 
         industry_vertical, created_at, settings JSONB)

-- ENTITY HIERARCHY (legal entities, cost centers, projects)
entities (id, tenant_id, parent_id, name, type, currency, 
          is_consolidation_entity, metadata JSONB)

-- CHART OF ACCOUNTS
accounts (id, tenant_id, code, name, type[asset/liability/equity/revenue/expense],
          sub_type, is_calculated, normal_balance, tags, gl_code_map JSONB)

-- DIMENSIONS (departments, products, channels, geographies — extensible)
dimensions (id, tenant_id, type, code, name, parent_id, metadata JSONB)

-- TIME PERIODS
periods (id, tenant_id, year, month, quarter, fiscal_period,
         is_closed, closed_at, closed_by)

-- SCENARIOS / VERSIONS
scenarios (id, tenant_id, name, type[budget/forecast/actual/strategic],
           base_scenario_id, locked_at, created_by, description)

-- THE FINANCIAL FACT TABLE (core — all numbers live here)
financial_facts (
  id, tenant_id, entity_id, account_id, scenario_id, period_id,
  dimension1_id, dimension2_id, dimension3_id,  -- extensible dimensions
  amount DECIMAL(28,10),  -- never FLOAT
  currency VARCHAR(3),
  amount_reporting DECIMAL(28,10),  -- converted to reporting currency
  fx_rate DECIMAL(18,8),
  source[manual/imported/calculated/ai_forecast],
  source_ref,  -- integration reference
  entered_by, entered_at, approved_by, approved_at,
  note, is_deleted, version
)

-- AUDIT TABLE (immutable append-only)
audit_log (
  id, tenant_id, user_id, action, entity_type, entity_id,
  field_changed, old_value, new_value, ip_address, session_id,
  occurred_at, metadata JSONB
)

-- DRIVERS (for driver-based models)
drivers (id, tenant_id, scenario_id, name, formula, 
         unit, period_id, value DECIMAL(28,10), dependencies JSONB)

-- HEADCOUNT
headcount_records (id, tenant_id, entity_id, scenario_id, period_id,
                   employee_id, role, level, department_id,
                   start_date, end_date, base_salary DECIMAL(18,2),
                   currency, status[active/open/departed], 
                   employment_type, metadata JSONB)

-- INTEGRATIONS
integrations (id, tenant_id, type, name, config_encrypted, 
              last_sync_at, sync_status, field_mapping JSONB)

integration_sync_log (id, integration_id, started_at, completed_at,
                      records_processed, records_failed, error_log JSONB)

-- REPORTS
saved_reports (id, tenant_id, name, type, config JSONB, 
               created_by, is_public, schedule JSONB)
```

### Critical Data Rules

```
RULE D1: amount columns are always DECIMAL(28,10), never FLOAT/DOUBLE/NUMERIC without precision.
RULE D2: All monetary storage includes currency code. Bare numbers are forbidden.
RULE D3: Actuals are immutable after period close. Amendments create new records.
RULE D4: Every financial_fact has a traceable source chain.
RULE D5: FX rates are stored with the fact, not recomputed on read (prevents restatement bugs).
RULE D6: Soft deletes only (is_deleted) — financial data is never physically purged.
RULE D7: Multi-tenancy is enforced at DB row level (RLS), not application level only.
RULE D8: Indexes on (tenant_id, period_id, entity_id, account_id, scenario_id) — all query paths.
```

## XVIII-I. Section 6 — Financial Engine Specification

### Engine Architecture

```
FinancialEngine
├── FormulaParser      (Excel-compatible syntax, dependency graph, cycle detection)
├── CalculationGraph   (DAG-based, topological sort, incremental recalc)
├── PrecisionLayer     (decimal arithmetic, rounding rules, currency conversion)
├── ConsolidationEngine (multi-entity, eliminations, minority interest, FX translation)
├── AllocationEngine   (percentage, headcount, revenue, custom driver methods)
├── ScenarioEngine     (version branching, comparison, delta computation)
├── ForecastEngine     (statistical methods: linear, exponential smoothing, ML)
├── VarianceEngine     (absolute, %, favorable/unfavorable, drill-path)
├── CashFlowEngine     (direct + indirect method, free cash flow, working capital)
├── CapExEngine        (asset register, depreciation methods: SL/DB/SOYD/UOP)
├── HeadcountEngine    (FTE calc, comp modeling, benefits load, attrition)
└── ValidationEngine   (balance sheet checks, cash flow reconciliation, assertions)
```

### Formula Engine Rules

```
RULE F1: Circular dependency detection before any calculation (fail fast, not silent).
RULE F2: Calculation order is deterministic (topological sort of dependency DAG).
RULE F3: Rounding is applied at output layer, not mid-calculation.
RULE F4: Division-by-zero produces NULL with a logged warning, never NaN or Infinity.
RULE F5: Formula errors surface to the user with the formula text + offending value.
RULE F6: All formulas are stored as AST, not string — enables safe serialization.
RULE F7: Formula changes trigger incremental recalculation (only affected nodes).
RULE F8: FX translation follows IAS 21: P&L at average rate, BS at closing rate,
         CTA goes to equity. This is non-negotiable and must be tested.
```

### Three-Statement Integrity Rules

```
RULE TS1: Net Income from P&L must flow to Retained Earnings on BS. 
          Automated assertion test runs after every calculation.
RULE TS2: Cash on BS must equal ending cash on Cash Flow Statement.
          Automated assertion test. Any mismatch is Severity-0.
RULE TS3: Total Assets = Total Liabilities + Total Equity at all times.
          Automated assertion with alert on any violation.
RULE TS4: These three assertions run after EVERY save, import, and calculation.
          They cannot be disabled.
```

# PART XIX — FINANCIAL DATA INTEGRITY PROTOCOLS
# ═══════════════════════════════════════════

*(New article — FP&A-specific, K18-supreme)*

## XIX-A. The Arithmetic Contract

```
NEVER use IEEE 754 floating point for monetary values.
NEVER compare monetary values with == (use decimal epsilon or exact decimal comparison).
NEVER truncate — always round explicitly with documented rounding rule.
NEVER store currency-agnostic amounts (every amount has a currency code).
NEVER aggregate across currencies without explicit FX conversion.
NEVER silently drop precision (log + alert on any precision loss).
```

Violation of any NEVER above is a **Severity-0 defect** blocking all other work.

## XIX-B. The Immutability Contract

```
Actuals in closed periods: IMMUTABLE.
  → Any correction is an adjusting entry, not an edit.
  → Corrections are versioned and audit-logged.

Locked scenario versions: IMMUTABLE.
  → New scenarios branch from locked ones; locked ones do not change.

Audit log: APPEND-ONLY, IMMUTABLE.
  → No UPDATE or DELETE on audit_log. Ever.
  → Implement at DB level (trigger or policy), not just application layer.
```

## XIX-C. The Reconciliation Contract

After every data import or bulk calculation:

```
Reconciliation Report must show:
  - Total records imported vs total records processed
  - Sum of imported amounts vs sum in DB (must match to 2 decimal places)
  - FX conversion reconciliation (source amount × rate = converted amount)
  - Any records rejected with reason
  - Three-statement check result

If ANY reconciliation check fails: import is rolled back. 
User sees clear error with actionable fix instructions.
NEVER silently swallow import errors.
```

## XIX-D. The Period-Close Protocol

```
When a period is closed:
1. Run three-statement integrity check. Must pass.
2. Run reconciliation check against source system.
3. Lock all financial_facts for that period (DB-level constraint added).
4. Snapshot the scenario state to an immutable archive.
5. Generate close package (TB, P&L, BS, CF) and store as PDF artifact.
6. Send close confirmation to configured recipients.
7. Log close event to audit_log with approver.

Period close is irreversible via API. Requires explicit admin action to reopen.
Reopening is logged, requires reason, and creates an audit event.
```

## XIX-E. The FX Rate Protocol

```
FX Rate Sources (in priority order):
1. User-entered rates (highest trust — board-approved budget rates)
2. Feed from integrated source (ECB, OpenExchangeRates API)
3. Manual import (CSV of rates per period)

Rate Types (all stored, user selects per report):
  - Opening rate (first day of period)
  - Closing rate (last day of period)
  - Average rate (arithmetic mean of daily rates in period)
  - Budget rate (locked at budget start — does not change)
  - Custom rate (user-defined for scenario)

IAS 21 Default Application:
  P&L accounts    → Average rate
  BS accounts     → Closing rate
  Equity accounts → Historical rate (when transaction occurred)
  CTA             → Balancing figure to equity (auto-calculated)

All rate applications are stored with the translated amount.
Reports can be run at any rate type for comparison.
```

# PART XXI — AI/ML MODULE SPECIFICATION
# ═══════════════════════════════════════════

*(New article — FP&A AI layer)*

## XXI-A. AI Design Principles

```
AI-P1: AI assists; it never overwrites without explicit user confirmation.
AI-P2: Every AI-generated number shows its confidence interval.
AI-P3: AI forecasts are a separate scenario, not a mutation of user data.
AI-P4: Model explainability: user can ask "why did you forecast this?"
AI-P5: AI accuracy is tracked over time (forecast vs actual score).
AI-P6: AI never fabricates data; it operates only on data in the platform.
AI-P7: LLM calls for NLQ never send raw financial data to external APIs
       without explicit tenant consent and data processing agreement.
```

## XXI-B. Forecasting Engine

```
Methods available (user selects, or auto-selected by data characteristics):
  1. Naive (last period value / last year same period)
  2. Linear regression (trend line)
  3. Exponential smoothing (Holt-Winters with seasonality)
  4. ARIMA / SARIMA (statistical time-series)
  5. Prophet (Facebook/Meta — handles holidays, seasonality)
  6. Gradient boosting (XGBoost/LightGBM — when drivers available)
  7. Ensemble (weighted average of above methods)

Auto-selection criteria:
  < 12 periods of history → Naive or Linear
  12–36 periods          → Exponential Smoothing
  > 36 periods           → ARIMA or Prophet
  Driver data available  → Gradient Boosting

Output always includes:
  - Point estimate (median)
  - Confidence interval (P10, P50, P90)
  - Method used + why
  - Accuracy score of this method on historical hold-out
```

## XXI-C. Natural Language Query

```
Phase 1 (rule-based NLQ):
  Pattern library covering 50+ common financial queries:
  "What drove the variance in OpEx in Q3?"
  "Show me headcount by department for 2024"
  "Compare budget vs actual for revenue"
  → Parsed to structured query → executed against DB → rendered as chart/table

Phase 2 (LLM-augmented NLQ):
  - LLM converts freeform query to structured query (SQL or API call)
  - Only schema metadata sent to LLM (no actual financial values)
  - Results fetched from DB directly (LLM never sees the numbers)
  - User sees SQL generated (inspectable, trustworthy)
  
Privacy guarantee: Financial values NEVER sent to external LLM API.
Only schema, column names, dimension values (non-sensitive) used for query generation.
```

# PART XXIV — DATA LINEAGE & PROVENANCE GRAPH
# ═══════════════════════════════════════════

*(New article — satisfying the auditor "drill-down" promise and SOX compliance)*

## XXIV-A. The Lineage Mandate

Every single number rendered in OmniPlan must have an unbroken, queryable chain of custody back to its origin. "I don't know where this number came from" is a Severity-0 defect.

```
Lineage Node Types:
  SOURCE:   (e.g., NetSuite GL, CSV upload, Manual Input, AI Forecast)
  TRANSFORM: (e.g., FX Translation, Allocation, Aggregation)
  CALCULATE: (e.g., Formula in cell, Gross Margin calc)
  OUTPUT:   (e.g., Dashboard Tile, Board Deck PDF, Report Line Item)
```

## XXIV-B. Lineage Storage Architecture

Do not use relational tables for deep lineage; use a graph structure or recursive CTE optimized for the purpose.

```yaml
lineage_graph:
  storage: Apache AGE (PostgreSQL extension) OR dedicated graph DB
  schema:
    Node(id, type, tenant_id, metadata JSONB)
    Edge(source_id, target_id, operation_type, timestamp, diff JSONB)
  
  rules:
    - Every financial_fact write emits a Lineage Node + Edge.
    - Every calculation emits Edges connecting inputs to outputs.
    - Graph is append-only.
    - Traversing the graph from Output -> Source must take < 50ms for 5 hops.
```

## XXIV-C. The Auditor View

The UI must provide a "Lineage Inspector" mode:
1. User clicks any cell in a grid or chart.
2. UI renders a visual DAG (Directed Acyclic Graph) of the number's history.
3. User can click any node in the DAG to see the exact state of the data at that point in time.
4. Exportable as a "Audit Proof Packet" (PDF containing the lineage graph + underlying transactions).

# PART XXV — WORKFLOW STATE MACHINES & APPPROVAL ENGINE
# ═══════════════════════════════════════════

*(New article — replacing ad-hoc boolean flags with deterministic state machines)*

## XXV-A. The State Machine Mandate

Financial workflows (budget submissions, period close, scenario locking) cannot be managed by loose boolean columns (`is_submitted`, `is_approved`). They must be enforced by explicit State Machines.

## XXV-B. Canonical State Machines

```yaml
Budget_Version_StateMachine:
  States: [DRAFT, IN_REVIEW, REWORK, APPROVED, LOCKED, ARCHIVED]
  Transitions:
    DRAFT -> IN_REVIEW: [submit()]
    IN_REVIEW -> APPROVED: [approve(role: FINANCE_ADMIN)]
    IN_REVIEW -> REWORK: [reject(reason)]
    REWORK -> IN_REVIEW: [resubmit()]
    APPROVED -> LOCKED: [lock()]  # Triggers immutability constraints
    LOCKED -> ARCHIVED: [archive(after: 12 months)]
  Guards:
    - Cannot transition to LOCKED if Three-Statement Integrity fails.
    - Cannot transition to IN_REVIEW if required dimensions are missing.

Period_Close_StateMachine:
  States: [OPEN, PRE_CLOSE, RECONCILING, CLOSED, REOPENED]
  Transitions:
    OPEN -> PRE_CLOSE: [start_close_cycle(day: -5)]
    PRE_CLOSE -> RECONCILING: [trigger_erp_sync()]
    RECONCILING -> CLOSED: [finalize_close(requires: dual_approval)]
    CLOSED -> REOPENED: [force_reopen(admin_only, requires: reason)]
  Guards:
    - Cannot CLOSE if reconciliation report has exceptions.
    - Reopening a period automatically invalidates downstream rolled forecasts, triggering recalculation.
```

## XXV-C. Workflow Engine Implementation

Use a deterministic state machine library (e.g., `xstate` for TS, `transitions` for Python).
- State transitions are transactional with the data mutation.
- Every transition emits an Audit Log event.
- UI renders the current state and available next-actions based strictly on the machine definition and user role.

# PART XXVI — EXTENSIBILITY & USER-DEFINED FUNCTIONS (UDF)
# ═══════════════════════════════════════════

*(New article — solving the "Excel power user" gap)*

## XXVI-A. The UDF Mandate

Excel power users leave Excel because they can write custom VBA/macros. OmniPlan must provide a secure, sandboxed equivalent. If a user needs a calculation the formula engine doesn't natively support, they must be able to write it.

## XXVI-B. WebAssembly (Wasm) Sandbox Architecture

Never use `eval()`. Never run user code on the main thread or backend core process.

```yaml
udf_architecture:
  language_supported: AssemblyScript (TypeScript-like syntax that compiles to Wasm)
  execution_environment:
    frontend: Web Worker running Wasm module
    backend: Wasmtime / Wasm edge runtime
  capabilities:
    - Math operations, loops, conditionals
    - Read access to passed cell ranges (as typed arrays)
  limitations_enforced:
    - NO network access (fetch/http banned)
    - NO filesystem access
    - Memory limit: 64MB per function execution
    - CPU time limit: 2000ms per function execution
  api_surface:
    function define(name: string, fn: (inputs: Range[]) => Range)
```

## XXVI-C. UDF Lifecycle

1. User writes UDF in UI editor (monaco editor).
2. UI compiles to Wasm, runs dry-run against sample data.
3. UDF saved to DB as Wasm bytecode + source + AST.
4. Formula Engine recognizes `Custom.MyFunction()` syntax, routes to Wasm runtime.
5. Execution failures (timeout, OOM) return a safe `#UDF_ERROR!` without crashing the calculation DAG.

```
  - Dashboard load (10 widgets, heavy aggregation): < 1.5s.
```

## XXIX-B. The Incremental Calculation DAG

The formula engine cannot recalculate the whole model on every keystroke.

```
Architecture:
  1. Dependency Graph: Built once on model save. Nodes = cells, Edges = formula refs.
  2. Topological Sort: Maintained in memory.
  3. On Cell Change:
     a. Mark node dirty.
     b. Traverse downstream subgraph, mark all dependent nodes dirty.
     c. Execute recalculation ONLY on dirty nodes, in topological order.
     d. Push updated values to frontend via WebSocket.
  4. Bulk operations (imports) batch dirty-marking, then execute once.
```

```
     A 1B-cell model is a lie if stored densely.
ST4: Aggregate navigator: precompute common grains (entity×account×month).
ST5: CQRS: writes → facts + outbox; readers may hit replicas or cubes.
ST6: Cube lag SLO published in UI ("actuals as of 03:12 UTC").
ST7: Columnar export (Parquet) to customer warehouse (Snowflake share / S3).
ST8: Arrow flight optional Phase 3 for partner BI — does not replace OmniPlan UI.
ST9: Compression + encryption of partitions at rest.
ST10: Hot / warm / cold tiers: current FY hot; prior FY warm; 6+ years cold.
```
