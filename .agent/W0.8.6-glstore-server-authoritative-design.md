# W0.8.6 — glStore Server-Authoritative Design Note (Spike, read-only)

Status: DRAFT — implementation BLOCKED on W0.3 (runtime three-statement gate) landing.
Author: GL-Spike · Date: 2026-08-22
Governing rules: K25 (server is source of truth; client stores are draft state),
K27 (never last-write-wins on a decimal; cell-level optimistic versioning + typed conflicts).

## 1. Current state shape (`src/store/glStore.ts`, 797 lines)

Persisted slice (`partialize`, L765–769), storage key `gl-store` via `masterStorage`
(persist middleware, L760–770):

| Field           | Type           | Role today                                                                      |
| --------------- | -------------- | ------------------------------------------------------------------------------- |
| `entries`       | `GLEntry[]`    | The official GL data — **this is the problem**: it is authoritative client-side |
| `importHistory` | import records | Import audit trail                                                              |
| `columnMapping` | mapping config | Import wizard UX preference                                                     |

Transient (not persisted): `accounts`, `trialBalance`, `accountAnalysis`,
`dateFilter`, `accountFilter`, `isLoading`, `importProgress/Status/Error`,
`lastImportResult`, `lastImportEntryIds`.

Derived/recomputable: `trialBalance` (L301–352, Decimal-accumulated per F-0006),
`accountAnalysis` (L354–410). Both are pure functions of `entries` + `accounts`.

Mutation actions that write `entries` (all currently local-only):
`setEntries` (L179), `addEntries` (L201), `importGLData` (L216),
`addEntry` (L278), `undoLastImport` (L482), `clearData` (L432).
Undo/redo via module-level `UndoRedoEngine<GLSnapshot>` (L65, L149–175).

Validation already client-side and reusable as pre-flight:
`validateEntries` (L533–625) includes the F-0004 double-entry invariant
(exact integer cents, zero tolerance, grouped by `journalId`).

Cube integration: `syncToCube`/`syncFromCube` (L629–748) push/pull `GL_Actuals`
cells into the local cubeStore — becomes a downstream projection of server data.

## 2. Persistence path today

Client-only: zustand `persist` → `masterStorage` → localStorage key `gl-store`.
No round-trip to the server from this store.

Server counterpart already exists and is tenant-scoped (W0.2):
`server/src/routes/gl.ts` — GET list / POST single / bulk POST / DELETE /
trial-balance join against `gl_entries`; every statement carries
`tenant_id = ?` resolved from the JWT claim (`resolveTenantId` never trusts
client input). Schema: `gl_entries(id PK, tenant_id NOT NULL DEFAULT 'default',
environment_id NOT NULL DEFAULT 'dev', account_id, entity_id, post_date,
amount, debit, credit, description, reference, department_id, created_by,
created_at)` — see `server/src/db/tenancy.ts` L36 (environment-scoped registry)
and `bootSchema.test.ts`. Leak tests green (`gl.tenancy.test.ts`).

Gap vs client shape: the server row set has no `journalId`, no `period`/
`periodName`, no `idempotencyKey`; client entry ids are generated client-side
(`gl-${timestamp}-${index}`), which will collide with server-assigned identity.

## 3. Target architecture (K25)

Three tiers:

1. **Server (authoritative):** `gl_entries` rows + trial balance. Only the
   server may finalize numbers.
2. **Client store (draft):** glStore keeps its current shape but `entries`
   becomes _draft/uncommitted_ state. Renamed conceptually: `draftEntries`
   kept under the same field initially to limit blast radius, with a
   `syncState` marker per entry (`'draft' | 'pending' | 'committed' | 'failed'`).
3. **Projection caches:** `trialBalance` / `accountAnalysis` recomputed locally
   for UX over committed data, always re-fetched (or revalidated) after commit.

Persistence split:

- `columnMapping`, view filters → stay client-persisted (UI prefs, K25-safe).
- `entries` → removed from `partialize` once server sync is live; during
  migration keep persisted drafts with a `dirty` flag and drain-to-server on boot.
- `importHistory` → moves to server (it is an audit artifact; K25 retention).
- Undo/redo stack stays client-local (session UX only); undo of a committed
  entry must become a compensating server DELETE, not local history replay.

## 4. Actions: server round-trip vs draft-local

**Become server round-trips (official numbers):**

- `setEntries` / `addEntries` / `addEntry` / `importGLData` → validate locally
  (existing `validateEntries`, cheap rejection before network) then POST to
  `/api/gl` or `/api/gl/bulk`; store returns server ids; entries flip
  draft→committed only on 2xx. `importGLData` keeps its dedupe
  (`checkDuplicates`) as a client pre-filter; server remains final arbiter.
- `undoLastImport` / `clearData` → server deletes scoped by the stored
  `lastImportEntryIds` batch token (needs a server-side import-batch id column
  or idempotency key — see §7).
- `syncToCube` → unchanged mechanically, but should run off committed data
  returned by the server, never off drafts.
- Trial balance reads → GET `/api/gl/trial-balance` (already tenant-scoped);
  local `generateTrialBalance` demoted to optimistic preview of drafts only.

**Stay draft-local:**

- `filterByDate` / `filterByAccount` / `clearFilters`, `updateColumnMapping`,
  `setImportProgress/Status/Error`, undo/redo stack, toasts.
- In-progress upload staging rows (before user confirms import).

**RBAC note:** all mutating actions are already wrapped in `enforce(Permissions…)`
— keep those wrappers as the client gate; the server route middleware
(`requireEntityWriteAccess`) remains the real enforcement point.

## 5. tenantId / environment_id flow (from W0.2)

- Client **never sends** tenantId. Server resolves it from the JWT claim via
  `resolveTenantId` (gl routes already do this; login does not yet sign
  tenantId claims — W0.2b dependency).
- Client supplies `environment_id` explicitly per working context (dev/prod
  selector from W0.2's environments table); default `'dev'` until W0.2.2
  backfill flips default to prod.
- Store gains `activeTenantContext: { environmentId }` (tenant implied by
  auth token). Every request goes through `FpaClient` (src/sdk/FpaClient.ts,
  supports tenant segment in path options) rather than raw fetch, per the
  "no fetch in components/services" convention.
- On boot: hydrate committed entries with `GET /api/gl?environment_id=…`;
  drafts persisted locally are keyed by `(environmentId)` to prevent
  cross-environment draft bleed.

## 6. Conflict handling (K27)

Never last-write-wins on any decimal. Protocol:

1. **Optimistic versioning:** each committed `gl_entries` row (or journal
   batch) carries an integer `version` (and `updated_at`). Reads capture it;
   writes send `If-Match: version`.
2. **Batch granularity:** imports/journals commit atomically as a batch —
   either the whole balanced journal lands or none (matches F-0004 gate and
   W0.3 three-statement gate which will reject unbalanced writes server-side).
3. **Conflict response:** `409 CONFLICT` with typed payload from
   `server/src/types/errorCodes.ts` (registry built for exactly these gates):
   `{ code, table, serverVersion, serverRow }`.
4. **Resolution UI:** typed outcomes only —
   - non-overlapping edit → auto-rebase onto serverVersion, retry once;
   - monetary divergence → surface both values side-by-side, require explicit
     human choice; no silent merge;
   - deleted-on-server → drop draft with notice (K25: retention beats erasure;
     server tombstone wins for financial records).
5. **Integrity assertion:** after every commit/rebase, re-run the F-0004
   debit=credit check and the trial-balance delta assertion client-side;
   mismatch ⇒ mark store degraded, block further commits, show error.
