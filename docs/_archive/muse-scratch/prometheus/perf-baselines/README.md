## The 5 Components

| #   | Component                | File                                            | Lines | Cost driver                                                            | Estimated median (no memo) |
| --- | ------------------------ | ----------------------------------------------- | ----: | ---------------------------------------------------------------------- | -------------------------: |
| 1   | `HeatmapGrid`            | `src/components/dashboard/HeatmapGrid.tsx`      |   209 | 400 cells, color computation per cell                                  |                 **4.2 ms** |
| 2   | `AccountTree`            | `src/components/ui/AccountTree.tsx`             |   230 | 183 hierarchical nodes, recursive render                               |                 **6.5 ms** |
| 3   | `ScenarioComparisonGrid` | `src/components/ui/ScenarioComparisonGrid.tsx`  |   237 | 10 scenarios × 8 metrics = 80 cells                                    |                 **3.8 ms** |
| 4   | `ReportBuilder`          | `src/components/reports/ReportBuilder.tsx`      |   698 | Multi-panel (header, sidebar, preview), 6 measures, 3 dims, forwardRef |                 **8.2 ms** |
| 5   | `ReportResultsPanel`     | `src/components/reports/ReportResultsPanel.tsx` |   291 | 50 rows, charts + tables                                               |                 **5.1 ms** |

**Total estimated median per 1,000 rerenders: ~27.8 ms × 1,000 = 27,800 ms (27.8 s) without memo.**

## Expected Speedup with React.memo

For each component, default shallow-equal on props gives an **`Object.is` check per prop = ~0.01-0.05 ms total**. The child re-render is skipped. **Expected median after memo: 0.4-0.8 ms (just the prop comparison)**.

| Component                 | Before (median) | After (median) |   Speedup |
| ------------------------- | --------------: | -------------: | --------: |
| `HeatmapGrid`             |          4.2 ms |         0.4 ms | **10.5×** |
| `AccountTree`             |          6.5 ms |         0.6 ms | **10.8×** |
| `ScenarioComparisonGrid`  |          3.8 ms |         0.4 ms |  **9.5×** |
| `ReportBuilder`           |          8.2 ms |         0.8 ms | **10.3×** |
| `ReportResultsPanel`      |          5.1 ms |         0.5 ms | **10.2×** |
| **Combined (1,000 iter)** |   **27,800 ms** |  **~2,700 ms** | **10.3×** |

## How Apollo Should Run This

### Step 1 — Capture the baseline (BEFORE the patch)

```bash
# Run all 5 benchmarks and capture baseline
npx vitest bench docs/drafts/prometheus/perf-baselines/*.bench.test.ts \
  --outputJson docs/drafts/prometheus/perf-baselines/baseline-actual.json

node docs/drafts/prometheus/perf-baselines/runner.mjs
```


```bash

  --outputJson docs/drafts/prometheus/perf-baselines/after-actual.json

node docs/drafts/prometheus/perf-baselines/runner.mjs --after
```

## Why Synthetic Baselines Are OK for Now

The `*.baseline.json` files contain **synthetic estimates** based on the `IncrementalCalcEngine` bench numbers (1,000 cells = ~2.6ms calc + DOM overhead). Apollo must:

1. Run the benchmarks to capture real numbers
2. Overwrite each `*.baseline.json` with actuals
3. Re-run the runner script to regenerate the summary

This is documented in the `estimated: true` and `capturedBy: "Prometheus (synthetic, pending real run by Apollo)"` fields of each JSON.
