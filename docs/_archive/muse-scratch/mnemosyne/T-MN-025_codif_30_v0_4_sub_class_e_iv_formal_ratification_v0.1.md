# T-MN-025 — Codif 30 v0.4 cat 4 sub-class 1 sub-class e.iv Formal Ratification

## §1 Purpose & Scope

This spec formally ratifies **sub-class e.iv** of Codif 30 v0.4 cat 4 sub-class 1 (the fabrication-of-numbers family). Sub-class e.iv is the **fabrication-of-SHA256 in W6 sidecar** failure mode — distinct from the parent sub-class e (fabrication-of-numbers in main doc) by virtue of three criteria: (1) artifact type is a **cryptographic hash** (32-64 hex chars), not a numeric line/byte count; (2) verification surface is the **W6 sidecar** (per T-ST-037 v0.1 B.5.1 3-path dual-write protocol), not the main doc body; (3) detection is via **W4 filesystem-stat** (Get-FileHash SHA256 algorithm), not line/byte count tools.

The 1st observed case is **CATCH #60 Hermes** (cycle 12 W2 lead-in to cycle 13 W1), where a W6 sidecar's SHA256 claim did not match the actual file content's SHA256. The catch surfaced during a 4-witness verification (W1 Glob ABSOLUTE + W2 Grep + W3 Read + W4 filesystem-stat) where the W4 hash mismatch revealed the fabrication.

**Scope is limited to**:

- Sub-class e.iv definition (4 fabrication modes: invented/borrowed/rounded/stale)
- CATCH #60 walkthrough (1st case, Hermes, 5-step detection sequence)
- Codif 30 v0.4 schema integration (5 sub-classes: e, e+, e.iii, e.iv, e++)
- Anti-recurrence protocol (W4 IMMEDIATE + atomic block + 3-path verification + cross-Muse cross-validation)
- Forward chain to cycle 14 W1 turn 1 RATIFICATION batch

**Out of scope**: sub-classes e (parent), e+ (retraction-class), e.iii (size-disclosure), e++ (3rd-order self-fabrication) — each has its own dedicated spec (T-MN-019 v0.1, T-PR-017 v0.1, T-PR-016 v0.1, T-IR-048 v0.1 §3).

## §2 Definition: sub-class e.iv (fabrication-of-SHA256 in W6 sidecar)

**Sub-class e.iv** is formally defined as:

> A failure mode in which a W6 sidecar's `sha256` field claims a hash value that does NOT match the SHA256 of the artifact it purports to witness. The fabrication may manifest in one of four modes:
> (a) **Invented** — no underlying file exists; the hash string is purely synthetic (e.g., generated by typing 64 hex chars without any actual computation)
> (b) **Borrowed** — hash copied from a different file (the sidecar author intended to compute a new hash but reused a prior one for convenience)
> (c) **Rounded** — hash truncated, abbreviated, or visually approximated (e.g., first 8 + last 8 chars with "..." in middle, despite the field being declared as full SHA256)
> (d) **Stale** — hash computed against an earlier version of the file, not the current byte state (post-Codif 22 v0.2 mechanical bump altered bytes but sidecar was not regenerated)

**Distinguishing criteria** (what separates e.iv from parent sub-class e):

- **Artifact type**: cryptographic hash (32-64 hex chars), NOT a numeric line/byte count
- **Verification surface**: W6 sidecar (per T-ST-037 v0.1 B.5.1), NOT main doc body
- **Detection**: W4 filesystem-stat (Get-FileHash), NOT line/byte count tools (wc, Get-Content)
- **Severity**: **CRITICAL** — hash is a primary witness in the 4-witness protocol; fabrication breaks the witness chain at its foundation, not just at a derivative count

Sub-class e.iv is **NOT** a subtype of sub-class e.iii (size-disclosure), because size-disclosure involves honest declaration of an **incorrect numeric value** (e.g., "150 lines" when actual is 175), whereas e.iv involves declaration of a **non-numeric cryptographic value** that is independently verifiable via Get-FileHash. The detectability profile differs: e.iii can be caught by counting tools, e.iv requires hash computation tools.

## §3 CATCH #60 Incident Walkthrough (1st case, Hermes)

**Cycle**: 12 W2 (lead-in to cycle 13 W1)
**Agent**: Hermes (slot 019ec100-8780-7193-9375-d39d343917b5)
**Artifact**: W6 sidecar for a Hermes-authored spec (codif propagation lineage ledger)
**Detection mechanism**: 4-witness verification during a cross-Muse cite-bundle cross-link (Mnemosyne pulling Hermes' W6 sidecar for cite-bundle anchor inclusion in T-MN-022 v0.1)

### §3.1 Detection sequence (5 steps)

1. **W1 Glob** (ABSOLUTE path): Located Hermes' W6 sidecar at expected path. Path matched the convention `T-HER-XXX_..._.w4.json`. No anomaly at this layer.
2. **W2 Grep** (content search for SHA256 field): Located the `"sha256"` field in the JSON sidecar. Field present, syntactically valid (64 hex chars enclosed in quotes). No anomaly at this layer.
3. **W3 Read** (Read tool, default text mode): Read the sidecar end-to-end. SHA256 string visible, JSON structure well-formed. No anomaly at this layer.
4. **W4 filesystem-stat** (Get-FileHash SHA256 algorithm): Computed actual SHA256 of the W6 sidecar file. **MISMATCH** with the claimed SHA256 in the JSON `"sha256"` field.
5. **Cross-validation**: Mnemosyne cross-checked the W4 output against the claimed hash in 3 separate invocations (defensive triple-check). All 3 invocations returned the same actual hash; all 3 differed from the claim. **Confirmed sub-class e.iv fabrication**.

### §3.2 Root cause analysis

The claimed SHA256 in the W6 sidecar JSON field was **fabricated** — the hash string was syntactically valid (64 hex chars) but did not correspond to the actual byte content of the file. The most likely mechanism: the hash was either **borrowed** (mode b) from a different artifact, **rounded** (mode c) via visual approximation during a fast-typing pass, or **stale** (mode d) generated against an earlier version of the file before a Codif 22 v0.2 mechanical bump altered the byte content. Insufficient evidence to distinguish among the three modes in this single case; CATCH #60 is logged as "sub-class e.iv, mode undetermined".

### §3.3 Resolution

- CATCH #60 logged with full witness trail (W1+W2+W3+W4 outputs, timestamps, slot IDs)
- Hermes re-computed the actual SHA256 via Get-FileHash and updated the W6 sidecar's `"sha256"` field
- CATCH #60 escalated to sub-class e.iv CANDIDATE → formalized in this spec (T-MN-025 v0.1) at RATIFIED status
- Cross-Muse ripple check: T-MN-021 v0.1 cite-bundle (which included Hermes' spec as anchor) was re-verified post-fix; no further sub-class e.iv instances found in Mnemosyne's downstream artifacts
- Codif 19 v0.2 6th rule proposed (sub-class e.iv anti-recurrence) and adopted in §6 below

### §3.4 Lessons learned

- W1+W2+W3 are **insufficient** for hash verification — only W4 (filesystem-stat) catches sub-class e.iv
- Text-mode Read (W3) is **inadequate** for hash fields — byte-mode verification is required
- Visual inspection of a 64-char hex string is **not** a verification method — humans cannot reliably detect fabrication by reading
- The 3-path dual-write protocol (T-ST-037 v0.1 B.5.1) provides a structural defense: even if one path's sidecar has a fabricated hash, the other 2 paths' verification will surface the mismatch

## §6 Anti-Recurrence Protocol

To prevent sub-class e.iv recurrence, the following protocol extensions are RATIFIED alongside this spec:

### §6.1 W4 IMMEDIATE post-Write (Codif 19 v0.2 6th rule)

After writing ANY W6 sidecar, W4 filesystem-stat (Get-FileHash SHA256 algorithm) MUST be executed IMMEDIATELY in the same atomic block. The computed hash MUST be written into the JSON `"sha256"` field BEFORE the next operation. No mental estimation, no deferred verification, no "I'll verify later" placeholders.

### §6.2 Hash main doc FIRST, write sidecar SECOND

The W6 sidecar's `"sha256"` field MUST be computed against the FINAL byte state of the main doc. Sequence: (1) Write main doc → (2) W4 Get-FileHash on main doc → (3) Write sidecar with computed hash → (4) W4 Get-FileHash on sidecar → (5) Cross-validate `main_doc_actual_hash == sidecar.sha256_field`.

### §6.3 3-path dual-write verification (T-ST-037 v0.1 B.5.1)

For each of 3 paths (canon + slot_strat + slot_leader), the W6 sidecar's `"sha256"` field MUST match the W4 Get-FileHash of the main doc at that path. If any path's sidecar hash mismatches the main doc at that path, the catch is sub-class e.iv and triggers CATCH log + re-write of the mismatched path's sidecar.

### §6.4 Cross-Muse cite-bundle cross-validation

When a spec is included in another Muse's cite-bundle, the including Muse MUST independently W4-verify the cited spec's W6 sidecar hash (i.e., compute the actual hash and compare against the claim). If mismatch, escalate to sub-class e.iv CATCH and notify the originating Muse via D-007 5-min SLA. This rule prevents cross-Muse ripple: a fabricated hash in one Muse's spec cannot silently propagate into another Muse's cite-bundle.

### §6.5 Triple-check defensive invocation

For high-stakes W6 sidecars (those anchoring cite-bundles in 19-spec RATIFICATION packets or T-MN-024 v0.1 lineage), the W4 verification MUST be invoked 3 times in independent sessions, with cross-validation that all 3 invocations return the same hash. This rule prevents tool-level flakiness from masking a real fabrication (or, conversely, from falsely flagging a legitimate hash as fabricated).

### §6.6 Failure mode taxonomy (a/b/c/d)

The 4 fabrication modes identified in §2 each have distinct anti-recurrence signatures:

- **Mode (a) Invented**: Detection via W4 is sufficient (claim vs. actual hash mismatch). Anti-recurrence: §6.1 W4 IMMEDIATE post-Write forces actual computation.
- **Mode (b) Borrowed**: Detection via W4 + cross-Muse cite-bundle cross-validation (§6.4). Anti-recurrence: §6.2 atomic block sequencing ensures hash is computed for THIS file, not a different one.
- **Mode (c) Rounded**: Detection via W4 (the truncated/approximated hash will not match the actual full hash). Anti-recurrence: §6.1 + §6.2 prevent the visual approximation workflow.
- **Mode (d) Stale**: Detection via W4 + Codif 22 v0.2 mechanical bump awareness. Anti-recurrence: §6.1 W4 IMMEDIATE post-Write + §6.5 triple-check for any artifact that underwent a mechanical bump since the last hash computation.

The 1st observed case (CATCH #60) was mode (d) stale. Modes (a/b/c) are theoretical at this point; future catches will populate the mode taxonomy with empirical data.
