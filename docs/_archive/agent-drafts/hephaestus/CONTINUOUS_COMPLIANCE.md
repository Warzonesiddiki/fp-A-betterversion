## §1 Why continuous compliance (post-Type 2)

Type 1 attestation (2027-03-31 per T-HEP-007 §5) is a point-in-time snapshot. Type 2 attestation (2027-10-31) is a 6-month observation window. **After Type 2, the SOC 2 controls must keep operating effectively — not just on audit day, but every day.** This is the gap T-HEP-008 closes.

**3-witness (rule / evidence / consequence):**
- **Rule:** SOC 2 Type 2 requires controls to OPERATE EFFECTIVELY over the 6-month observation window. The auditor samples 1-2 quarters of evidence (not just the final week).
- **Evidence:** T-HEP-007 §4 Type 2 row: "Auditor verifies controls OPERATE EFFECTIVELY over 2027-04-01 to 2027-09-30 (6-month minimum observation window)."
- **Consequence:** Without continuous evidence collection, the auditor's sample will likely catch a control gap (e.g., a stale access review, a missed vuln scan) → Type 2 has findings → Type 2 attestation delayed → enterprise sales blocked.

**The 3 inputs to continuous compliance:**
1. **4 locked ADRs** (006 data-retention, 007 encryption-at-rest, 008 audit-logging, 009 incident-response) — the controls we operate
2. **Vanta platform** (T-HEP-007 recommendation) — the automation backbone
3. **Existing stack** (GitHub, AWS, Datadog, Sentry, Okta, HRIS) — the source systems

**The 2 outputs:**
1. **Quarterly evidence binder** — automatically generated by Vanta, reviewed by Hephaestus, archived in S3 Object Lock (per ADR-008)
2. **Annual Type 2 audit** — auditor reads the quarterly binders + samples specific controls

## §2 The 5 quarterly SOC 2 controls

These are the 5 controls the auditor tests **every quarter** during the Type 2 observation window. Each control has a specific evidence format, owner, and SLA.

| # | Control | CC criterion | Evidence format | Owner | Quarterly SLA | Vanta automation |
|---|---|---|---|---|---|---|
| 1 | **Access reviews** | CC6.1 | SSO log diff (active employees vs active accounts), RBAC matrix snapshot, terminated employees removed within 24h | Hephaestus + Atlas | Q+30 days | Vanta + Okta/Azure AD integration |
| 2 | **Vulnerability scanning** | CC6.8 | Snyk + Dependabot scan results, mean time to remediate (MTTR), exception register | Apollo + Hephaestus | Q+15 days | Vanta + Snyk + Dependabot |
| 3 | **Backup verification** | CC7.5 | Backup logs, restore test results, RTO ≤ 4h / RPO ≤ 1h validation | Atlas | Q+45 days (post-restore) | Vanta + AWS S3 + R2 cold archive |
| 4 | **Incident response tabletop** | CC7.3 | Tabletop scenario, participant list, lessons learned, ADR-009 update | Hephaestus (facilitator) | Q+60 days (within the quarter) | Vanta + manual facilitation |
| 5 | **Policy attestation** | CC1.4 | Policy version, attestation signatures (all employees + contractors), training completion | Hephaestus + HR | Q+75 days (or continuous) | Vanta + HRIS (Gusto/Rippling) + LMS |

**The 5 controls map to the 4 ADRs (per Athena T-AT-008 verdict):**
- Access reviews → ADR-007 (encryption key access), ADR-008 (audit log access)
- Vulnerability scanning → ADR-007 (crypto CVE monitoring), ADR-009 (plugin sandbox CVE)
- Backup verification → ADR-006 (7-year SOX retention), ADR-008 (audit log S3 Object Lock)
- Incident response tabletop → ADR-009 (NIST SP 800-61 lifecycle)
- Policy attestation → ADR-006 (retention policy), ADR-007 (encryption policy), ADR-008 (audit policy), ADR-009 (IR policy)

### §2.1 Control failure modes + exception handling

Each quarterly control has a known set of failure modes. The exception handling is the playbook for when the control fails.

| Control | Failure mode | Detection | Exception handling | SLA |
|---|---|---|---|---|
| **Access reviews** | Terminated employee not removed within 24h | Vanta diff alert (active SSO - active HRIS) | Hephaestus manually removes access + documents in Vanta; root-cause analysis if >24h | 24h detection → 4h fix |
| **Vulnerability scanning** | High-CVE not remediated within 7 days | Vanta Snyk/Dependabot alert | Apollo fixes or accepts risk (with written justification); Vanta tracks SLA breach | 7d detection → 14d fix or accept |
| **Backup verification** | Restore test fails (data loss or RTO/RPO breach) | Atlas manual test | Atlas re-runs restore + escalates to Hephaestus; root cause + remediation plan | 1d detection → 7d fix |
| **IR tabletop** | Tabletop finds critical gap (e.g., comms template missing) | Hephaestus observation | Hephaestus updates ADR-009 within 7d; re-tabletop within 30d | Same-quarter resolution |
| **Policy attestation** | Employee refuses to sign or training incomplete | HRIS alert | HR follows up; Hephaestus escalates if >30d non-compliant | 30d detection → 7d HR follow-up |

**The 5 controls are the auditor's quarterly checkpoints.** If any control has an unresolved exception at quarter end, the Type 2 evidence binder flags it; the auditor's sample will likely catch it.

## §3 The 4 evidence-collection scripts (Vanta automation)

Vanta integrates with our stack via 4 categories of scripts. Each script is a pre-built Vanta integration OR a custom Lambda/Cloud Function that pulls evidence on a schedule.

| # | Script | Source system | Evidence pulled | Schedule | Format | Vanta integration |
|---|---|---|---|---|---|---|
| 1 | **GitHub → Vanta** | `github.com/<org>/<repo>` | PR approvals, branch protection rules, code review evidence, signed commits, SECURITY.md presence | Real-time webhook | JSON | Pre-built Vanta integration |
| 2 | **AWS/GCP → Vanta** | `aws.<org>` + `gcp.<org>` | IAM config (admin users, MFA enabled), S3 bucket policies (public access blocked), security groups (SSH not 0.0.0.0/0), KMS key rotation | Daily | JSON | Pre-built Vanta integration |
| 3 | **Datadog/Sentry → Vanta** | `datadoghq.com` + `sentry.io` | Alert configs, PagerDuty rotation, MTTD/MTTR, error rates, uptime SLO compliance | Hourly | JSON | Pre-built Vanta integration |
| 4 | **HRIS → Vanta** | `gusto.com` OR `rippling.com` | Employee onboarding/offboarding events, training completion, policy attestation signatures, background check status | Daily | JSON | Pre-built Vanta integration (Gusto + Rippling) |

**3-witness on the 4 scripts:**
- **Rule:** Vanta's "automated evidence collection" claim is in T-HEP-007 §3 (200+ hours of audit prep saved). The claim is credible only if the 4 scripts work.
- **Evidence:** Vanta public integration list shows 300+ integrations including GitHub, AWS, GCP, Datadog, Sentry, Gusto, Rippling. All 4 source systems are supported out-of-the-box.
- **Consequence:** If any of the 4 scripts fails silently, the auditor will find a control gap in the quarterly binder. Hephaestus runs a weekly "Vanta integration health check" (15 min) to catch failures.

**Custom scripts (none in v1):** All 4 evidence sources have pre-built Vanta integrations. No custom Lambda functions needed in v1. If we add a 5th source (e.g., Snowflake for data warehouse), that may need a custom script.

### §3.1 Script validation + failure recovery

Each Vanta script needs:
- **Initial validation** (one-time, 4 hours per script): verify the script can pull the expected evidence format (JSON, schema validation), test against a known-good state, document the script's API endpoint + auth method
- **Continuous monitoring** (weekly 15 min per script): Hephaestus runs a "Vanta integration health check" — checks that the last sync timestamp is within the expected window, validates a sample of evidence items, flags silent failures
- **Failure recovery** (when a script breaks): Hephaestus triages the failure (Vanta platform issue vs source system issue), re-authenticates if needed, escalates to Vanta support if platform issue

**The 4 scripts have different failure recovery SLAs:**
- **GitHub → Vanta:** near-zero failure rate (Vanta's most stable integration). Recovery: 1h to re-authenticate.
- **AWS/GCP → Vanta:** low failure rate (IAM rotation can break it). Recovery: 4h to rotate credentials.
- **Datadog/Sentry → Vanta:** medium failure rate (API key rotation, Sentry upgrades). Recovery: 4h.
- **HRIS → Vanta:** low failure rate but HIGH business impact (employee onboarding/offboarding). Recovery: 24h (requires HR coordination).

**The weekly integration health check is the early-warning system.** Hephaestus runs it every Monday morning; the 4 scripts are checked in order of business impact (HRIS first, GitHub last). Any silent failure is escalated within the same week.

### §4.1 Disaster recovery for the continuous compliance system

The continuous compliance system itself needs a DR plan. If Vanta goes down, our SOC 2 evidence collection is paused; if our source systems go down, Vanta pulls stale data; if Hephaestus goes down, the weekly health check is missed.

**3 failure scenarios + recovery:**

| Failure | Detection | Impact | Recovery SLA | Owner |
|---|---|---|---|---|
| **Vanta platform outage** | Vanta status page + Hephaestus weekly check | Evidence collection paused; quarterly binder delayed | 4h (Vanta 99.9% SLA per contract) | Vanta + Hephaestus (manual evidence gathering) |
| **Source system outage** (GitHub, AWS, Datadog/Sentry, HRIS) | Vanta sync timestamp stale | One of the 4 scripts broken | 1-24h per source | Apollo + Atlas + HR (per script) |
| **Hephaestus unavailable** (PTO, illness) | Weekly check missed | Quarterly review delayed | 1 week (slack allows) | Founder covers (per T-HEP-007 §6 RACI) |

**Manual evidence gathering (Vanta outage):** If Vanta is down for >24h, Hephaestus manually exports evidence from the 4 source systems (GitHub PR list, AWS IAM snapshot, Datadog alert config, HRIS report) and archives to S3 Object Lock. The auditor accepts manual evidence as long as it's hash-stamped and time-stamped.

**The Atlas T-ATL-008 Disaster Recovery Runbook (5 scenarios, 7 sections, completed 2026-06-13) covers the broader DR posture** (database, app, infra). T-HEP-008 §4.1 is the SOC 2-specific overlay.

## §5 Quarterly cadence (the 4 × 90 min per year)

Each quarter has a 90-min review cycle. The cadence is repeatable + auditable.

**Q+15 (Week 3 of quarter):** Vulnerability scan review
- Apollo runs the Snyk + Dependabot scan review (15 min)
- Hephaestus reviews exceptions (30 min)
- Decisions: fix now / fix next sprint / accept risk (with justification)

**Q+30 (Week 5 of quarter):** Access review
- Atlas pulls the SSO + RBAC diff (15 min, automated)
- Hephaestus reviews terminated employees + new joiners (30 min)
- Actions: remove stale access within 24h, document exceptions

**Q+45 (Week 7 of quarter):** Backup verification
- Atlas runs the backup + restore test (60 min, manual)
- Hephaestus signs off on RTO/RPO (15 min)
- Actions: update RTO/RPO targets if needed, document test results

**Q+60 (Week 9 of quarter):** Incident response tabletop
- Hephaestus facilitates (60 min)
- All Muses participate (90 min total including prep)
- Output: tabletop report, ADR-009 update if needed, action items

**Q+75 (Week 11 of quarter):** Policy attestation
- HRIS pulls the attestation queue (automated)
- Hephaestus reviews completion rate (15 min)
- Actions: chase non-attesters, update policies if needed

**Q+90 (Week 13 of quarter):** Quarterly binder generation
- Vanta generates the evidence binder (automated)
- Hephaestus reviews + signs off (30 min)
- Archive to S3 Object Lock (per ADR-008 §Migration)

**Total quarterly effort: ~6 hours per quarter × 4 quarters = 24 hours/year for Hephaestus.** Plus 90 min × 4 = 6 hours/year for all Muses (tabletop). Net: 30 hours/year for continuous SOC 2 compliance.

## §9 Continuous improvement (the meta-loop)

T-HEP-008 is not a one-time setup — it's a **meta-loop** that improves the SOC 2 controls over time. The loop has 4 steps:

1. **Observe** — Vanta surfaces exceptions (e.g., "Snyk found 3 high-CVEs in `decimal.js` not remediated within 7 days")
2. **Orient** — Hephaestus triages the exception: is it a real gap or a false positive?
3. **Decide** — Hephaestus updates the relevant ADR (e.g., ADR-007 adds a "7-day CVE remediation SLA" clause) or accepts the risk with justification
4. **Act** — Apollo implements the change; Vanta validates the new control on the next quarterly run

**The 3 improvement sources (per Athena T-AT-005 ship-readiness gaps):**
1. **Vanta exceptions** — automated signal
2. **Tabletop lessons learned** — quarterly signal
3. **Pen-test findings** — annual signal (per T-HEP-005)

**The 3-witness discipline applies to every improvement:**
- **Rule:** Every continuous improvement must be a 1-line change to an ADR (or a new ADR if material)
- **Evidence:** Athena T-AT-008 verdict: 4 ADRs have 0 fabrications. Same discipline must apply to future updates.
- **Consequence:** Drift from the ADR is the #1 way SOC 2 controls fail between audits. The meta-loop prevents drift.
