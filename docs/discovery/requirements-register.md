# Initial Requirements Register

**Status:** Draft proposals; validate during audit and product discovery.  
**Priority:** P0 = foundation/release gate; P1 = core workflow; P2 = later capability.  
**Status vocabulary:** Proposed / Accepted / Rejected / Deferred / Implemented / Verified.

| ID | Priority | Requirement | Acceptance criteria (draft) | Status | Target evidence (2026-10-15, base `04c329e`) |
|---|---|---|---|---|---|
| FR-001 | P0 | The user can identify the scope of each monthly dataset. | Period, source identity, entity (if present), currency (if present), and import time are stored or explicitly marked unavailable; the UI does not imply an unknown scope. | Proposed | **Partial (branch).** Each batch records `scope {periods, dateRange, entities | 'unavailable', currencies | 'unavailable', importedAt}` and the Done step shows "not in file" rather than a default. Still open: source-system identity (which D365 company/legal entity the export came from) — needs DEC-001. |
| FR-002 | P0 | The import validates the agreed export schema before analysis. | Missing/renamed required columns and invalid values produce actionable errors; no row is silently discarded; behavior is covered by fixtures. | Proposed | **Partial (branch).** Store: any validation error rejects the whole batch (atomic) and returns one `VALIDATION` rejection per bad source row; possible ledger overlaps are `DUPLICATE_ROW` with their source row and reject the whole file (DEC-009), not a filtered remainder; rows the page could not parse now abort the whole file with structured source-row reasons (DEC-007); no entries or success history are committed, and a corrected retry is allowed. Rejected-attempt history is not yet durable. Still open: the real D365 schema contract (DEC-001). Row parsing is now a pure function (`src/services/import/parseGLRows.ts`) with fixture tests for missing/whitespace account codes, missing/malformed/calendar-invalid dates, unparseable and locale-formatted amounts, multi-fault rows, empty files and purity. Tests: `src/services/import/parseGLRows.test.ts`, `src/store/glStore.provenance.test.ts`, `GLUploadPage.deep.test.tsx`. Preview parity (2026-10-17): `GLDataPreview` now validates **every** row through the same `parseGLRows` the import uses — it no longer ran a second, disagreeing rule set (float `parseFloat`, 20-row window, blank amounts rejected) — names rejected rows by source-file row with the importer's reason (including rows past the display window), and blocks confirmation; the interop test proves the gate blocks source row 26 and that the store does not move (`GLDataPreview.test.tsx` 26 tests, `GLUploadPage.interop.test.tsx` 7 tests). |
| FR-003 | P0 | Import results are reproducible and protected from accidental duplicates. | Re-importing the same file is detected or handled by an explicit documented policy; test verifies no unintended duplicate financial effect. | Proposed | **Met at store level (branch).** `importGLData` rejects a file whose SHA-256 (or canonical row-content hash for connector imports) already succeeded; the repeat has no state effect and names the prior batch id. Policy: reject, never merge. Test: `glStore.provenance.test.ts` (FR-003 cases). |
| FR-004 | P0 | The system provides import control totals and reconciliation status. | For the agreed scope, row counts and financial controls are independently computed and shown; differences prevent a “reconciled” status. | Proposed | **Partial (branch).** `computeControlTotals` (decimal, cent-exact) is computed independently of the trial-balance engine for every committed batch and shown on the Done step and in history. ## Requirement governance

- Give every accepted requirement an owner and decision date.
- Split requirements when their acceptance criteria cannot be tested together.
- Link each accepted requirement to implementation issues and verification tests.
- Do not mark “Implemented” until code exists; do not mark “Verified” until evidence passes.
- Add explicit data-source prerequisites to every metric and anomaly rule.
