# Audit-chain reachability and authority map

**Inventory baseline:** measured 2026-10-19 on `arena/b72c910a-fp-a-betterversion` at the N2 audit-chain consolidation slice. **Current-session N2 follow-up:** 2026-10-20 on `arena/d9a8f733-fp-a-betterversion`, based on the verified PR #78 merge commit. This is an evidence map, not a declaration that the audit authorities have been consolidated.

## Current N2 result

`auditTrailStore` is the only client audit trail in this inventory that is both persisted and currently used as an audit chain by a user-facing general audit page. `AuditTrailPage` now subscribes to its persisted entries and adapts its schema to the existing table/export model. The page no longer reads a module-level `CellAuditTrailEngine` instance.

The standalone `AuditLogger` remains in the source tree for its isolated snapshot API, but has no production caller or persistence adapter. Historical security and accessibility documents that describe integrations are not evidence that those integrations are wired.

**Current-session lineage verifier follow-up (2026-10-20):** a failing-first regression showed `verifyIntegrity()` returned `true` when the unkeyed entry hashes were intact but the chain's cached `currentValue` contradicted its last hashed entry. The verifier now also validates that each chain is non-empty, map/chain/entry cell IDs agree, and `currentValue`, `createdAt`, `changeCount`, and `uniqueActors` match the verified entries. `getCurrentValue()` reads the final entry's value rather than trusting the cached summary. `cellLineageStore.test.ts` now passes 20/20; combined lineage/audit/page/persistence run: 6 files / 59 tests. Two failing-first regressions also require the persisted `pendingEntries` compatibility mirror to match the hashed chain entries one-to-one and exactly; both were reproduced before the check was added and pass now. The initial bounded persistence proof was the first case in `src/store/cellLineageStore.persistence.test.ts` (1/1 when recorded) and a then-current 5-file/38-test lineage/storage/audit run. It used real `masterStorage` encryption/decryption and fresh-module hydration while a persistent in-memory SQL.js adapter mock retained ciphertext. Those are historical counts; the expanded follow-up evidence appears in the DEC-029 section below. No persistence schema or producer was added; N2 remains active.

This does **not** close N2. There are additional persisted domain chains, an active but in-memory SOX log path, a server `audit_log` that documentation calls authoritative but the frontend does not call, and multiple unconsumed/test-only implementations. Their owners/authority boundaries are recorded below; none is silently treated as retired or equivalent.

## Compatibility and migration evidence

`CellAuditTrailEngine` held only module memory and had no production producer or persistence adapter; DEC-027 retires it. Its former page entries therefore could not survive a reload, so there is no durable legacy dataset to migrate. The UI compatibility boundary maps `auditTrailStore`'s persisted `CellAddress`, epoch-millisecond timestamp, `previousValue`, `approvalUserId`, and optional display aliases into the existing row model. CSV export redacts the original canonical store record rather than casting a display row into the store type.

The persistence compatibility test now exercises the store's declared v0→v1 Zustand migration contract against a representative legacy payload: it asserts the v1 version, preserves entries and `chainHead`, confirms only integrity-bearing fields are persisted, and verifies the restored chain. This is a migration-contract unit test plus state-restore integrity check; it does not simulate the encrypted/native masterStorage backend or a native restart.

Evidence: `src/pages/audit/AuditTrailPage.test.tsx` — 20 passing tests; `src/store/__tests__/auditTrailPersistence.test.ts` — 7 passing tests, including v0→v1 compatibility; `npm run tsc` and `npm run format:check` passed. `npx eslint src/domain/persistenceAuthority.ts src/store/__tests__/auditTrailPersistence.test.ts --max-warnings 0` passed. The earlier full-lint attempt timed out at 180 seconds and reported a Prettier issue in `src/domain/persistenceAuthority.ts:67`, now fixed; `npm run lint` subsequently passed in 121.9 seconds on the DEC-027 slice. `docs:verify` and `engines:verify` passed. `docs:links --strict` first found four pre-existing broken backtick citations in the plan/backlog; those citations were corrected and the final strict link check passed with 0 broken links or citations.

## DEC-029 cell-lineage retention and repair evidence

A failing-first persistence contract test demonstrated that JSON round-tripping v1 `cell-lineage-store` produces `chains: {}` rather than a `Map`; a second test demonstrated that the old `verifyIntegrity` accepted a modified `newValue` because it checked only predecessor links. Both failures were observed before the fix (2 failing new cases). DEC-029 retains the namespaced local-draft store because persisted `pendingEntries` may contain user history; no empty-history claim or deletion is made.

The store now persists chains as a JSON record, revives them to `Map`, and migrates v1 `{}` chains by rebuilding from the append-ordered `pendingEntries`. Integrity verification recomputes unkeyed SHA-256 for the same ordered fields written by v1 and checks each previous-hash link; it resets global/per-chain verified state on hydration. With no external anchor, a complete rewrite can recompute the chain. Unit contract covers both current v2 round-trip and v1 reconstruction, plus altered-payload rejection. `cellLineageStore.test.ts` passes 12/12; the combined lineage/audit-page/persistence run passed 3 files / 39 tests. `npm run tsc`, full `npm run lint` (176.0s), targeted ESLint, `npm run format:check`, `docs:verify`, `engines:verify`, strict `docs:links`, and `git diff --check` passed after the repair. The full sharded suite and pre-push remain unrun; `metadata` remains outside the digest. A later bounded test, `src/store/cellLineageStore.persistence.test.ts`, passed 2/2, and the combined lineage/storage/audit run passed 5 files / 38 tests at that point. It exercises real `masterStorage` encryption/decryption and fresh-module hydration; one case uses a persistent in-memory SQL.js adapter mock and another exports/reopens a real SQL.js/WASM database image through the test adapter. A subsequent `src/store/cellLineageStore.sqljsPersistence.test.ts` adds a round-trip through the production `sqlJsStorage` implementation and real SQL.js/WASM database image backed by localStorage; it passes 1/1. After the pending-entry mirror consistency guard was added, the combined lineage/audit/page/persistence run passed 6 files / 59 tests. Final integration after these fixes: `npm run check` passed, including 8/8 shards in 1,154s (shard 8 reported 1,946 passed and 1 skipped; the sharder does not provide an aggregate test count). These tests establish a bounded browser-storage/module-reload contract only—not native Tauri SQL persistence, OS-key custody, native disk durability, or an actual application-process restart. Those proofs remain open.

Native Tauri SQL persistence, OS-key custody, and actual application-process restart remain unverified; metadata is not hash-covered.
